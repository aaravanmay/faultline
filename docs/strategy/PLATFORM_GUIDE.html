faultline Cofounder brief · 2026
Chaos engineering for AI agents

The failure no one is testing for.

AI agents are starting to take real actions — placing orders, moving money, shipping code. When a tool feeds one bad data, it doesn't crash. It confidently does the wrong thing, with no error. faultline catches that, on purpose.

This is a short brief on what faultline is, what already works, the honest state of it, and where it goes next — written for someone I'd want to build it with.

01The problem

Every test an agent passes assumes its tools behave. They don't. A search returns 3 of 47 results. An API hands back a stale price. A lookup returns a plausible-but-wrong number. The agent has no idea — it reasons over the broken data and acts:

Your agent doesn't crash.
It lies.

It places the order on a wrong quantity. It refunds the wrong customer. It quotes last week's number as today's. No crash, no alert, every test green. Evals measure quality when everything works. Monitors watch the pipes. Security tools chase attackers. None of them break the tools on purpose to find the silent wrong answer — the one that actually costs money once an agent can act.

02Why this wins

Honest picture: the room is no longer empty. "Agent chaos engineering" is being called the next frontier (Towards Data Science, VentureBeat), and Azure Chaos Studio, Fastio, and the eval tools (DeepEval, Pydantic Evals) are all moving in. But they're all crowding the easy half — and that's the opening.

  • Injection is commoditizing; detection isn't. Anyone can break a tool. The unsolved part is reliably deciding the agent then did the wrong thing — without a flaky LLM judge. That's where the false positives and the trust live, and nobody has nailed it.
  • We win on depth and a vertical, not the category name. Deterministic, fault-specific invariants (stale-data → did it flag staleness? wrong-number → did it act on an impossible value?), aimed at action-taking agents — coding, financial ops — where a silent-wrong has a price tag.
  • The hard part is already built. This grew out of my last project's interception engine — wrapping and intercepting an agent's tool calls. That primitive recorded failures; faultline turns it offensive and causes them.
  • Proof, not positioning. The category narrative is being written by others right now — we don't out-talk it, we out-prove it: be the one tool that catches the silent failure the eval/judge crowd structurally misses, demonstrated on a famous agent.

03What already exists

The reason I'm writing this and not just describing an idea: the 80% that's usually vaporware in a pitch is built and running.

Working today
  • The engine (Python, open-source): arms a fault, runs the agent, and classifies every result PASS / SILENT-WRONG / CRASH. It runs offline right now and catches a real silent failure — an agent that buys an out-of-stock item with no error. Six faults: timeout, server-error, truncate, null-response, stale-data, wrong-number.
  • CLI + GitHub Action. pip install faultline → faultline run fails the build the moment a tool fault makes the agent silently wrong.
  • The hosted platform. A real signed-in dashboard — resilience score over time, a per-fault matrix for every run, regressions — on a full auth + database backend. Plus the marketing site.
  • The loop is closed. faultline run --push sends CI results straight to the dashboard — metadata only, never your prompts or data. Tested end-to-end.

04The honest state

For a cofounder this matters more than the highlight reel:

Not done yet
  • No users, no revenue. It's built, not launched.
  • The dashboard demo data is illustrative — real data flows the moment a project token runs in CI.
  • The oracle is the real risk. Deciding "is the answer wrong?" currently leans on an LLM judge. That has to become deterministic (below). This is the #1 thing to de-risk.
  • Billing, team invites, public deploy — stubbed or pending.

05Where the real value is

This becomes a company, not a clever tool, when these land:

  1. Reposition: a CI regression gate, not a one-time audit. "Find your silent bugs" gets run once and uninstalled. The durable product is per-PR: "Resilience 87 → 71 — a new silent failure was introduced in this diff," posted as a comment on the pull request. Same engine, completely different retention.
  2. Fix the oracle with deterministic invariants. Instead of "is the answer wrong?", check fault-specific behavior that needs no ground truth: stale-data → did it flag the staleness? wrong-number → did it act on an impossible value? truncate → did it treat a partial list as complete? That library of fault → invariant checks is real, defensible IP.
  3. Build the moat from data. The engine is copyable in a weekend. The asset is the Agent Resilience Index: anonymized benchmarks across frameworks and faults — "your stale-data resilience is bottom-quartile for support agents." Nobody else has that data.
  4. Distribution: a content engine, not "Show HN and pray." A weekly "we broke a famous agent" post, plus the MCP wedge — "does your agent survive a misbehaving MCP server?" Narrow the focus to action-taking agents (coding, financial ops) where a silent-wrong has a price tag.

07How it's built (for the curious)

Web stackVanilla HTML / CSS / JS with GSAP, three.js and Lenis — no build step. A light marketing site and a dark, multi-page product app.
BackendSupabase — Postgres, Auth, and row-level security. One server-side ingest_run function is the only write CI can make, validated by a hashed project token.
